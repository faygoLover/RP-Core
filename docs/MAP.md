# RP Core — карта

Версия на момент написания: 0.15.0 (16.11.2026). Факты по классам, событиям, пакетам и командам — `docs/INDEX.md`.

## 1. Что делает и чего не делает

RP Core — связующая библиотека семейства RP-модов. Сам игровых механик не ведёт: даёт **механизмы** (мод
описывает, Core выполняет: данные игрока, привязка настроек, надетое в Curios, картинки, общий HUD) и **розетки**
(один мод регистрируется как поставщик, остальные спрашивают, не зная о нём). Любой мод семейства зависит только
от Core и работает при любом составе соседей: без поставщика розетка отвечает значением по умолчанию.

За этим — не сюда:
- механика одного мода (раны, голод, сон…) — в сам мод; в Core только то, что нужно двум и более;
- графика, шейдеры, цветной свет — FL Render;
- заплатки чужих модов и правила сервера S5 — RP Fixes;
- сама длина дня и ночи — RP Time (Core только знает, идёт ли время и с какой скоростью);
- инструменты ведущего и эффекты `red_eyes`, `interference` сейчас лежат здесь, но это не библиотека: уедут в
  отдельный мод (план, T5.1). Нового туда не добавлять.

## 2. Как течёт работа

**Регистрация.** Конструкторы модов идут параллельно → мод в конструкторе описывает данные
(`PlayerStore…register()`, `PersistentTag…register()`); в `FMLCommonSetupEvent` (`enqueueWork`) регистрирует
поставщиков (`RpCoreAPI.registerBody`, `registerMind`, `registerProvider`…), модуль и команды.
Списки поставщиков — в `RpCoreAPI`; хранилища — в `data/PlayerStores` (после первого `AttachCapabilitiesEvent`
список закрыт и выровнен по имени).

**Данные игрока.** игрок создаётся → `PlayerStores.onAttach` вешает данные каждого `PlayerStore` под его id →
сохранение и чтение — `PlayerStore.write/read` (с миграцией версии, если задана) → смерть или возврат из Края:
`PlayerStores.onClone` открывает данные прежнего игрока, зовёт правило `clone` каждого хранилища и переносит
разделы `PersistentTag` → вход, возрождение, смена измерения: `resync(игрок, причина)` → выход: `forget`.
Сбой одного мода не оставляет без данных остальные (каждый вызов в своём `try`).

**Вопрос к розетке.** мод зовёт `RpCoreAPI.body()` (или обёртку вроде `RpCoreAPI.unconscious(p)`) → Core отдаёт
зарегистрированного поставщика или ответ по умолчанию → мод обходится простой версией, если поставщика нет.
Что поставщик ведёт на самом деле — `BodyProvider.handles(id)`, `RpCoreAPI.nutritionHandles(id)`; id — в `RpIds`.

**Событие.** мод-источник шлёт событие Core в шину Forge (`MinecraftForge.EVENT_BUS.post`) → слушают все, кому
надо. Пример: `/rptime sleep` → `TimeCommand` → `RpTimeSkipEvent` → Medicine заживляет раны, Culinary тратит еду,
Needs восстанавливает сон.

**Время RP.** `time/RpTime`: идёт ли время (команда `/rptime` или внешний источник — RP Time через
`RpCoreAPI.registerTimeSource`), длина суток, скорость → `RpCoreAPI.bodyScale()` (RP-секунд за реальную; 0 на
паузе) → `bodyRate()` = `bodyScale() / BODY_REFERENCE` — множитель для долгих процессов.

**Клиенту.** свой канал `rpcore:main` (`network/CoreNetwork`): фото и картинки, анкета тела, доступ ведущего,
окно настроек ГМ-блоков, эффекты на сущностях, поза сна. Данные модов Core клиенту не возит — каждый мод шлёт
свои сам (из `resync`).

**HUD.** мод регистрирует `HudElement` в `client/hud/HudRegistry` → `CoreClient` рисует все элементы одним слоем →
раскладку (якорь, смещение, видимость) хранит `HudLayout` в `config/rpcore-hud.json`, правит редактор `/rphud`.

## 3. Карта пакетов

| Пакет | За что отвечает | С чего начать читать |
|---|---|---|
| `rpcore` | вход мода, общий конфиг | `RpCore` (все подписки на события видны списком), `CoreConfig` |
| `api` | всё, чем пользуются моды: точка входа, розетки, общие данные | `RpCoreAPI`, затем нужная розетка (`BodyProvider`…), `RpIds` |
| `api.data` | данные игрока, списки из датапака | `PlayerStore`, `PersistentTag`, `Matcher` |
| `api.config` | привязка настроек | `SettingsBinder` |
| `api.event` | события семейства | по имени события |
| `data` | внутренняя часть данных игрока | `PlayerStores` |
| `time` | время RP | `RpTime`; команда — `command/TimeCommand` |
| `pose` | позы `/sit`, `/lay`, сон `/sleep` | `Postures` |
| `profile` | анкета тела, вкусы, вайп персонажа | `ProfileServer`, `CharacterWipe` |
| `photo` | фото игроков и картинки по ключу (сервер) | `PhotoServer`, `PictureServer`; API — `api/Photos`, `api/Pictures` |
| `access` | «замок семейства»: скрытие предметов RP-модов без ключа ведущего | `RpAccess`, `AccessServer` |
| `command` | `/rpcore`, `/rpcore point`, `/rptime` | `CoreCommand` |
| `network` | канал `rpcore:main` и пакеты | `CoreNetwork` (порядок регистрации = номера пакетов) |
| `client` | клиентский вход, пустая рука, логины рядом с именами | `CoreClient` |
| `client.hud` | общий HUD и редактор | `HudRegistry`, `HudElement` |
| `client.photo` | фото и картинки на клиенте, снимок скина | `ClientPhotos`, `ClientPictures` |
| `client.access` | замок на клиенте, JEI | `ClientAccess` |
| `gm`, `client.gm` | **не библиотека:** невидимая пластина, держатели, метки на предметах, точки прибытия, окно настроек | `GmRegistry`; уедет в отдельный мод |
| `effect`, `client.effect` | **не библиотека:** эффекты «Красные глаза», «Помехи» | `RpEffects`; уедет в отдельный мод |
| `gametest` | игровые тесты Core (в релизный jar не идут) | `PlayerStoreTests` |

## 4. Хочу добавить… — рецепты

| Что | Где | Образец | Не забыть |
|---|---|---|---|
| новый вопрос к уже существующей розетке | метод `default` в интерфейсе розетки (`api/BodyProvider`…) + при желании обёртка в `RpCoreAPI` | `BodyProvider.infect`, обёртка `RpCoreAPI.unconscious` | ответ «не умею» по умолчанию; `@since`; имя не занято в моде-поставщике; реализация — в моде, отдельным коммитом там |
| новую розетку (поставщик один) | интерфейс в `api/`, поле `volatile` + `registerX` + обёртки в `RpCoreAPI` | `MindProvider` + `registerMind`, `stressImpulse` | обёртка возвращает понятное «нет поставщика»; тест в `gametest/CoreBricksTests` |
| розетку с несколькими поставщиками | `Map<ResourceLocation, X>` или список в `RpCoreAPI` | `LightProvider` + `registerLight` / `carriesLight`; `TraitProvider` + `registerProvider` | тот же id второй раз заменяет прежнего; порядок обхода не должен влиять на ответ |
| новое событие | класс в `api/event`, наследник `Event` | `RpMoodEvent`, `RpTimeSkipEvent` | кто шлёт и на какой стороне — в описании класса; каталог `FAMILY_MAP.md` §4 |
| общий id навыка, черты, части тела, возможности | константа в `api/RpIds` | `RpIds.BODY_HEALTH`, `RpIds.STRONG_WILLED` | id живёт в сохранениях и датапаках — не переименовывать |
| новый механизм для модов | класс в `api/…`, внутренняя часть — в своём пакете вне `api` | `PlayerStore` (api) + `PlayerStores` (внутри) | пример использования в описании класса; тест; запись в `CHANGELOG.md` |
| настройку Core | `CoreConfig` (общий, `rpcore-common.toml`) или `client/CoreClientConfig` | `SKIP_FLOOR` | описание по-русски; ключи не переименовывать |
| пакет клиенту или серверу | класс в `network/…Packets`, регистрация **в конце** `CoreNetwork` | `PosturePackets` | порядок регистрации — это номера пакетов: вставка в середину ломает совместимость клиента и сервера |
| команду | `command/…` + `bus.addListener` в `RpCore` | `PointCommand` | `RpCoreAPI.registerCommand` — чтобы попала в `/rpcore commands` |
| элемент HUD (в моде, не в Core) | реализация `HudElement`, `HudRegistry.register` в клиентской настройке мода | `MedicalHud.CoreElement` в RP Medicine | id элемента — ключ раскладки игрока, не менять |
| данные Core у игрока | `profile/ProfileServer` (раздел в `PlayerPersisted` — переживает смерть сам) | `rpcore_profile` | для нового — `PersistentTag` |

Изменение в Core, которого ждёт мод, выкладывается так: Core — версия +1 и сборка → `family.py sync` → мод
поднимает нижнюю границу `rpcore` в `mods.toml`.

## 6. Связи

- **FL Render** — обязателен на клиенте только из-за `client/effect` и `client/gm` (после T5.1 зависимость уйдёт).
- **Curios** — `compileOnly`; все обращения — во вложенном `Worn.Impl`. Без Curios `Worn` отвечает «ничего не надето».
- **Emotecraft** — позы с анимацией (`pose/EmoteImpl`), без него позы без анимации.
- **JEI** — `client/access/CoreJeiPlugin` (скрытие предметов), только API.
- **RP Time** — регистрирует источник времени; без него время ведёт `/rptime` и `CoreConfig`.
- Моды семейства Core не импортирует. Кто какую розетку реализует — `../_family/FAMILY_MAP.md` §4.

## 7. Конфиги

- `config/rpcore-common.toml` (`CoreConfig`, тип COMMON): разделы `commands` (`debug_commands`), `photo`
  (`min_interval_seconds`), `rptime` (`enabled`), `time` (`day_length_minutes`, `skip_floor`), `postures`
  (`enabled`, `stand_distance`), `access` (`gm_permission_level`). Обычный `ForgeConfigSpec`.
- `config/rpcore-client.toml` (`client/CoreClientConfig`): ключ ведущего, режим пустой руки, вид эффектов.
- `config/rpcore-hud.json` — раскладка HUD игрока.
- `SettingsBinder` — механизм для модов; сам Core им не пользуется.

## 8. Сеть

Канал `rpcore:main`, `network/CoreNetwork`. Номер пакета = порядок регистрации: новые — только в конец.
Клиенту не доверяется:
- фото и картинки: размер до 30 КБ и размеры из заголовка PNG проверяются до распаковки; картинка принимается
  только по разрешению сервера (`Pictures.allow`), фото — не чаще `min_interval_seconds`; запросы — с лимитом в секунду;
- анкета (`ProfilePackets.Submit`) принимается один раз, дальше её меняет только ГМ;
- настройки ГМ-блока (`GmPackets.Apply`) — только от ведущего, проверка на сервере (`GmTools`).

## 9. Ловушки

- **Конструкторы модов идут в разных потоках.** Регистрация хранилищ под замком, порядок вызова выровнен по имени
  хранилища. Не полагаться на порядок «кто раньше зарегистрировался».
- **Поздняя регистрация `PlayerStore`** (после начала загрузки мира) — исключение с объяснением: молча она
  оставила бы игроков без данных.
- **`LazyOptional`, закрытый вручную, не оживает.** Поэтому провайдер Core свой `LazyOptional` не гасит, а данные
  прежнего игрока при возрождении открывает `reviveCaps()` сам Core. Мод, который подпишет свой `invalidate`,
  останется без копии при смерти (так ломалась RP Stamina до 1.5.2).
- **Имя метода розетки может столкнуться со статическим методом поставщика** — мод перестанет компилироваться, а
  старый jar упадёт при вызове. Перед добавлением — поиск имени по семейству.
- **`SettingsBinder` и файлы на серверах.** Имя ключа, границы и текст описания определяют вид `toml`. Изменение
  правил перевода имён или границ по умолчанию меняет файлы у всех модов — нельзя.
- **Forge подтягивает число вне границ к ближайшей границе**, а не к значению по умолчанию; по умолчанию —
  только значение не того типа.
- **Пауза времени:** `bodyScale()` и `bodyRate()` на паузе равны 0 — долгие процессы стоят. Для подсказок
  «через сколько реальных минут» — `rpPerReal()` (без паузы).
- **`RpConsumeEvent` без мода питания** Core шлёт сам на `LivingEntityUseItemEvent.Finish` целым предметом; с модом
  питания, который ведёт укусы (`FOOD_PORTIONS`), — шлёт он. Двойной отправки быть не должно.
- **Замок семейства** (`access/`) включается только в локальной сборке с `lock.local.properties`; файл в git не идёт.

## 10. Тесты

`python ../_family/family.py verify --tests "RP Core"` — 17 игровых тестов (GameTest), идут без Curios:
- `PlayerStoreTests` (7): ветка в `ForgeCaps` под id хранилища, смерть, возврат из Края, вход/смена
  измерения/выход, версия и миграция, раздел `PersistentTag`, поздняя регистрация;
- `SettingsBinderTests` (4): файл совпадает до байта с собранным прежними вызовами (три стиля), чтение, границы, `set`;
- `CoreBricksTests` (6): `Worn` без Curios, эталон времени, `Matcher`, ответы розеток по умолчанию, психика и свет, достижение.

Добавил розетку или механизм — тест сюда же: ответ без поставщика и «вызов доходит». Тестовые хранилища
регистрирует `RpCore.registerTestData` только при запуске тестов самого Core.
